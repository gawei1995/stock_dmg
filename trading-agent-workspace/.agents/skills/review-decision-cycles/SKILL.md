# 决策周期复盘

## 建立周期

先选择一条复盘路径，再读取 [cycle-modes.md](references/cycle-modes.md)：

- `lightweight / retrospective`：默认先写三段简洁用户记录，再关联真实订单或自然月记录；不要求添加检查点或完成 blind，且必须明确标为回顾性分析。
- `rigorous / prospective`：用户确实要做事前预判时，封存当时信息并执行 blind → outcome。

周期范围支持：

- `trade_window`：由所选订单自动推导的单标的交易区间；投资理由可以是技术、基本面、催化剂、仓位管理或其组合。
- `catalyst`：财报、FOMC、产品发布、监管决定等离散事件。
- `position_lifecycle`：单一标的从首次建仓到清仓，或用户确认的阶段结束点。
- `monthly_portfolio`：一个自然月内实际发生的组合交易、敞口变化与协同风险。

为周期固定 `cycle_id`、`review_mode`、范围、时区、标的或账户范围和主要结果口径。月度轻量复盘自动扫描该自然月的账户记录，但主证据只纳入真实成交及能证明已成交或部分成交的父订单。纯未成交、取消、拒绝、过期和等待中订单，以及方向、数量、时间或价格无法核验的孤立成交，只保留在排除审计，不进入 Agent 结论、价格路径或验证样本。不要要求用户先重复建立一个空周期，也不要因日期接近而自动赋予交易理由。

## 轻量记录先行

执行 `retrospective` 前，先让用户留下三段简洁记录；短句有效，缺少内容时保留“暂无”，不要让 AI 代写用户原话：

1. `事后回忆的当时判断`（`retrospective_recollection`）：用户现在回忆当时相信什么、为何行动。始终标为事后回忆，不得冒充事前证据。
2. `本次感悟`（`current_reflection`）：用户现在认为做对、做错或尚不确定之处。只作为当前反思，不回填历史计划。
3. `从记录时点起生效的未来预判`（`future_forecast`）：用户对后续行情、动作或验证条件的当前预判。记录 `recorded_at` 与 `effective_from=recorded_at`；只对该时点之后有效，不能用于评价此前交易。

严格保留三个标签、用户原文、记录时间和各自 revision，不得合并、改名或将 AI 总结覆盖原文。AI 可以另建带来源的结构化版本，但必须与用户原话分栏。

轻量流程固定为：

`记录三段用户原话 → 关联券商订单/成交 → 校验关联范围与完整性 → AI 复盘`

单标的先记录，再由用户选择有效成交或已成交订单并补齐必要父子事实；月度先记录，再自动关联该自然月的有效交易事实。不得在券商事实关联完成前给出完整 AI 结论。

### 券商记录准入

- 将真实成交作为主事实；父订单只有在存在关联成交、`executed_quantity > 0`，或状态能证明已成交/部分成交时才进入主证据。
- 部分成交后取消仍是交易事实，必须保留已成交部分。
- 将纯未成交、取消、拒绝、过期、等待中订单标为 `audit_only`，默认隐藏且不可选择；按原因报告排除数量。
- 将方向、数量、时间或价格不可核验的成交标为 `audit_only`；保留原始券商字段用于数据审计，但不得进入 P&L、路径、动作评价或验证样本。
- 筛选政策改变后，将旧分析标为过期并以最新有效证据完整重跑，不得静默沿用旧结论。

## 直接事后复盘 — `retrospective`

1. 完成三段用户记录，再新建一个独立、持久的 Codex thread，并关联 `cycle_id`。
2. 关联通过准入的真实券商记录，读取周期内成交、有效父订单、可得行情和组合背景；单列排除审计，并披露缺失成交、费用、起止仓位或行情覆盖。
3. 将 `evidence_grade` 固定为 `retrospective`，并保持 `blind_assessment=null`。
4. 可以评价客观仓位路径、执行价格、风险暴露、结果和可验证的替代动作。
5. 没有事前封存时，不得正式评价“当时判断正确”“遵守计划”或“失效纪律”。

月度直接复盘不要求先逐笔建立单案例；单标的直接复盘不要求先选择催化剂或持仓生命周期类型。

### 重新关联券商记录

发现错选、漏选或错误归属时，不要覆盖或删除旧关联：

1. 保留原关联集合及其 `evidence_revision`，标记其被哪个 revision 取代。
2. 让用户重选记录；重新补齐订单与成交闭包，并校验标的、时间范围、方向、数量和成交覆盖。
3. 创建递增的新 `evidence_revision`，记录变更原因、时间、增删记录 ID 和确认人。
4. 将旧 AI 输出保留为历史产物，但标记 `stale`；不得把新证据追加到旧结论后假装已更新。
5. 使用最新有效 revision 重新运行完整 retrospective，并在结果中写明 `based_on_evidence_revision`。

## 执行强制两阶段

首次启动每个分析阶段时，必须新建独立、持久的 Codex thread，并用同一个 `cycle_id` 关联。用户在该阶段结果下继续追问时，复用当前 thread、对话历史和阶段证据；不要为普通追问再新建 thread。不要在 blind thread 中启动 outcome，也不要把另一个周期追加到当前 thread。

### Phase 1 — `blind`

1. 对每个决策检查点确定 `decision_at` 与 `cutoff_at`。
2. 只读取发布时间、写入时间或有效时间不晚于 `cutoff_at` 的证据。
3. 隐藏后续价格、财报结果、后续新闻、最终盈亏、MAE/MFE 和事后解释。
4. 按当时信息评价判断是否自洽、仓位是否匹配、计划是否可执行；不评价最终输赢。
5. 冻结 blind 输出、证据清单、缺失项和模型版本，生成不可覆盖的 `blind_assessment_id`。

若任何“事前”内容实际上在 cutoff 后生成或修改，将其标为 `retrospective`，不得用于正式评价判断质量、计划遵守或失效纪律。允许复盘客观执行事实，但必须降低结论等级。

### Phase 2 — `outcome`

1. 新建 outcome thread，引用同一 `cycle_id` 和已冻结的 `blind_assessment_id`。
2. 先原样呈现 blind 结论，再揭示 cutoff 后的基本面、技术路径、订单执行和结果。
   - 只有时间戳位于周期内的历史组合快照才能称为周期末证据；复盘时读取的当前组合必须单列为当前背景，不得反推周期末仓位、敞口或 P&L。
3. 分开评价决策质量、执行质量、结果质量与归因可信度。
4. 明确结果来自判断、技术时点、仓位、执行、市场 beta、运气或证据不足的可能程度。
5. 输出继续、验证、规避及候选规则；不要因盈利倒推判断正确，也不要因亏损倒推判断错误。

完整时间防火墙和证据标签见 [evidence-protocol.md](references/evidence-protocol.md)。

## 联合分析但保持变量独立

- 需要基本面、市场相信什么、预期差、叙事 Stage 或仓位框架时，联合使用 `analyze-market-narratives`。
- 需要价格结构、相对强弱、成交量、筹码、波动率或执行位置时，联合使用 `analyze-technical-structure`。
- 分开记录慢变量“市场叙事 Stage”和快变量“技术温度”；不要由其中一个直接推导另一个。
- 根据案例选择技术证据。EMA、Fib 只是可选基础工具，不是必填项或唯一技术框架。
- 保留用户原话，即使很短；AI 只能在 cutoff 前基于当时来源生成单独的事前结构化版本并让用户确认。cutoff 后的补写只能是回顾性重建。

## 处理证据不足

先报告覆盖率和不可计算原因。不得：

- 用当前持仓反推历史成交；
- 把订单意图当成实际成交；
- 用事后数据补写事前概率、失效位或计划风险；
- 将缺失值填为零；
- 让 Agent 推断冒充用户原话或事实。

缺少事前封存时，将周期或检查点标为 `retrospective`。此时可评价可验证的执行、风险暴露和结果，但判断质量、计划遵守与失效纪律必须标为“不可正式评价”。

## 治理规则

不要从一次复盘直接宣布规则。先让 AI 生成结构化验证草案，至少包含：假设、适用条件、动作、失效、主指标、次指标、观察窗口、样本纳入/排除、基准、预期机制、混杂因素、失败环境和留出验证。将草案展示给用户确认或编辑；未经用户确认不得登记为测试。

确认后的状态只能按以下顺序推进：

`候选 → 已登记测试 → 待人工 review → 试行 → 已验证`

单个周期只能提出候选；测试必须冻结样本纳入规则、主指标和留出集。AI 可以计算结果、整理证据并提出晋级建议，但每次规则登记、编辑和状态晋级都必须由用户明确确认；任何自动指标都不能越过人工 review 或自动提升规则。

## 输出顺序

1. 周期定义、阶段、thread 与证据 cutoff；
2. 数据健康和关联订单/成交；
3. 三段严格分栏的用户原话、记录时间与 AI 独立结构化；
4. blind 判断（冻结版本）；
5. outcome 揭示与动作时间线；
6. 决策、执行、结果、归因四分离；
7. 可计算指标及口径；
8. 继续 / 验证 / 规避；
9. 待用户确认/编辑的结构化验证草案、候选规则和下一次人工 review 条件。

在 blind 阶段只输出 1–4；不要提前生成 5–9 中依赖未来事实的内容。

在 retrospective 阶段跳过 blind 结论，先声明“无事前封存、不可正式评分的维度”，再按严格标签展示三段记录，注明证据 revision，输出订单/成交时间线、执行与结果、数据缺口、可验证改进，以及待用户确认/编辑的验证草案。
