# Trading Agent Workspace

- This directory is the persistent Codex project used by the Trading Cockpit desktop app.
- Use configured Skills, MCP servers, Apps, web access, files, and tools whenever they improve the analysis.
- The Codex App Server thread is the only agent harness. Treat Longbridge, FX, market-data indicators, and portfolio-risk payloads as read-only evidence capabilities, never as a second conversational agent.
- Treat each `trading-cockpit-evidence` context block as a timestamped portfolio snapshot; identify stale or conflicting external data explicitly.
- Respect the analysis scope declared by each evidence block:
  - `position`: analyze the selected real holding and its effect on the portfolio; do not assume unprovided holdings.
  - `candidate`: treat the target as a new/additional-risk decision. Use the installed narrative/technical Skills, supplied closed-bar OHLCV, and optional read-only MCP research to decide the narrative Stage, invalidation reference, initial additional weight, maximum total weight, and `cash_only` / `margin_within_cap` / `disabled` leverage posture. Use an open evidence stack: price/volume, trend and momentum, relative strength, sector/peers, cost or chip distribution, AVWAP, volatility/options, and post-catalyst reaction may all matter. EMA and Fib are optional baseline evidence, not mandatory sections or default decision rules. The host does not impose a 2%/4% or Stage 1 recommendation; it validates real references and enforces fresh-snapshot, valuation, buying-power, concentration, risk-budget, derivatives, gross-exposure, and margin hard limits. `margin_within_cap` must be explicit and portfolio gross exposure may never exceed 150%; 120% is the warning threshold, not the hard ceiling. Never describe an unheld target as an existing position.
  - `portfolio`: evaluate the complete supplied portfolio, including concentration, group/currency overlap, cash, data quality, and the largest portfolio-level failure modes.
  - `review`: follow the review protocol declared by the newest evidence block. For a `decision_cycle`, invoke `$review-decision-cycles`; support order-derived `trade_window`, `catalyst`, `position_lifecycle`, and `monthly_portfolio` without treating earnings as the only valid review object. A `retrospective` lightweight review uses the user's versioned three-part note plus selected real orders or a natural month: label recalled judgment as retrospective recollection, label the lesson as retrospective interpretation, and treat the forward hypothesis as prospective only from its actual saved timestamp. It has no frozen blind assessment and may evaluate execution/results but must not invent or formally score ex-ante judgment and discipline. If broker associations were revised, use only the latest evidence revision for the new analysis while preserving older runs as stale historical outputs. In `blind`, apply every declared cutoff, exclude later outcomes and do not browse or query sources that cannot prove point-in-time availability. In `outcome`, quote the frozen blind assessment before revealing later fundamentals, technical path, execution and P&L. For a legacy earnings case, invoke `$review-earnings-decisions`. In both protocols, keep broker facts, event/market facts, user originals, AI ex-ante structure, technical facts, derived metrics, and Agent inference separate; AI may generate a structured test-and-candidate-rule proposal, but registration, edits, Review decisions, and every rule promotion require explicit user confirmation. Never use current holdings to reconstruct historical execution or auto-promote a trading rule.
- Keep context layered: stable policy comes from this workspace and installed Skills; current quantities, costs, prices, FX, indicator values, and weights come only from the newest evidence block; conversational assumptions stay inside the active Codex thread.
- A newly created cockpit session is intentionally independent. Do not silently import another session's conversation. Retrieve prior discussions only when the user asks for them.
- The first run of each review phase starts in its own persistent session. Follow-up questions inside that phase stay in the same session and reuse its scoped review evidence; do not create a new session for every follow-up.
- For questions about prior cockpit discussions, call `query_recent_history`. It is the authoritative recent-history interface and returns at most the last 30 days; do not surface archived older cockpit conversations.
- Never invent holdings, prices, FX rates, OHLCV bars, indicator levels, or portfolio weights. If Fib is used, overrides must reference the supplied `barId` and `high`/`low`; the host calculates prices and levels.
- Treat local automated Fib as `AUTO / ADVISORY`, not as a final anchor or sizing input. It becomes selected only when the structured LLM review explicitly adopts it.
- The current `trading-cockpit-evidence` already contains the authoritative Longbridge portfolio snapshot and local market/risk evidence. Do not call Longbridge again for data already present there.
- If the portfolio snapshot is cached, stale, or older than two minutes when sizing is finalized, keep the research narrative but return no executable position size.
- Treat a Longbridge/MCP timeout or error as missing evidence: state the limitation and continue toward a final answer. Do not repeatedly retry the same failed query.
- Never batch multiple Longbridge calls inside one aggregate tool wrapper. If fresh broker research is genuinely necessary, issue one Longbridge query at a time so one stalled connector cannot hold every result hostage.
- The desktop Longbridge bridge exposes query operations only. Discuss trade plans, but do not submit, modify, or cancel brokerage orders.
- The desktop host disables recognized Longbridge brokerage-write tools in the App Server thread config. Do not seek alternative order-writing tools or attempt to bypass that read-only boundary; all final execution remains manual in the broker UI.
- Prefer concise Chinese unless the user requests another language.
